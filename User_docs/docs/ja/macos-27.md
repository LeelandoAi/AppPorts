# macOS 27 へのアップグレード

::: tip 要点
AppPorts で WeChat などのコンテナデータを移行し、そのとき再署名に同意した場合、macOS 27 へのアップグレード後に、ダブルクリックしてもアプリがすぐ終了する**可能性があります**。WeChat では発生し、QQ Music などは実測では引き続き開けました。**データは壊れていません**。移行をやり直す必要もありません。データをローカルに復元し、公式の配布元からアプリを再インストールすれば復旧できます。その後も外部ドライブに置きたい場合は、新しい[マウント移行](/ja/datamigrae/mount-migration)を使ってください。
:::

## 影響を受けるケース

| 項目 | 説明 |
|------|------|
| 発生条件 | macOS 27 へのアップグレード |
| 対象アプリ | `~/Library/Containers/` または `~/Library/Group Containers/` のデータを移行し、Ad-hoc 再署名を行ったアプリ。または右クリックから手動で再署名したサンドボックスアプリ |
| 典型的な症状 | Finder / Dock から開いても反応せず、アイコンが一瞬表示されて消え、エラーダイアログも出ない。ただし、再署名したすべてのアプリで起きるわけではなく、同じ macOS 27 で QQ Music は正常に動作した |
| データ | チャット履歴、ログイン状態を含めて正常 |
| 確認済みの例 | WeChat 4.1.15、macOS 27.0 (26A428) |

再署名によってアプリのサンドボックス ID が取り除かれたことが原因です。macOS 27 が「このアプリにこのコンテナを使う資格があるか」を確認するとき、システムに元の署名の許可記録が残っていると、新しい署名が一致せず拒否されます。WeChat のログには `Failed to match existing code requirement` と出ます。QQ Music など、古い記録がないアプリは現在は許可されますが、キーチェーンのログイン状態など、失われたエンタイトルメントは同様に戻りません。仕組みは[コンテナデータ、サンドボックスと署名 ID](/ja/datamigrae/container-identity)を参照してください。

## アップグレード前の確認

次のスクリプトで、AppPorts が署名を置き換えたアプリを一覧にできます。表示されたアプリは、アップグレード後に問題が起きる可能性があります。

```bash
BACKUP_DIR="$HOME/Library/Application Support/AppPorts/signature-backups"
for plist in "$BACKUP_DIR"/*.plist; do
  [ -f "$plist" ] || continue
  original=$(/usr/libexec/PlistBuddy -c "Print :signingIdentity" "$plist" 2>/dev/null)
  app=$(/usr/libexec/PlistBuddy -c "Print :originalPath" "$plist" 2>/dev/null)
  case "$original" in ""|ad-hoc) continue ;; esac   # 本来就是 ad-hoc 的跳过
  [ -d "$app" ] || continue
  if codesign -dv "$app" 2>&1 | grep -q "Signature=adhoc"; then
    printf "%s\n    原始签名: %s\n" "$app" "$original"
  fi
done
```

アップグレード前に、下の[修復](#修復)を済ませることをお勧めします。少なくとも一覧を控えておけば、アップグレード後にどのアプリを確認すべきか分かります。

## アップグレード後の症状確認

```bash
# 1. 签名（出现 Signature=adhoc 且 TeamIdentifier=not set 即已被重签名）
codesign -dv --verbose=4 /Applications/WeChat.app 2>&1 | grep -E "Authority|TeamIdentifier|Signature"

# 2. 复现并看系统日志
open -a /Applications/WeChat.app; sleep 3
log show --last 1m --style compact 2>/dev/null | grep -i "rejected approval request"
```

2 番目の手順で `kTCCServiceSystemPolicyAppData ... denied` が表示されれば確認できます。より詳しい確認表は[コンテナデータ、サンドボックスと署名 ID](/ja/datamigrae/container-identity#自分で確認する)を参照してください。

## 修復

AppPorts 1.8.2 は、この種類のアプリを自動検出します。アプリ一覧に赤い「署名置換済み」バッジが付き、起動時に一度通知します。右クリックから「修復手順を表示」を選ぶと修復パネルが開き、以下の順序で各手順の状態とボタンを表示します。処理中にデータを削除することはありません。手動操作でも同じ順序で行ってください。**順序は変えないでください。**

### 手順 1：コンテナデータをローカルに復元する

修復パネルの「すべて復元」をクリックします。または「データディレクトリ」→「アプリデータ」で対象のアプリを選び、「Linked」になっているコンテナディレクトリをすべて、一つずつ「Restore」してください。アプリはもともと起動できないため、実行中としてブロックされることはありません。

この手順を先に行う理由は、再インストール後のアプリが正常なサンドボックスアプリに戻り、シンボリックリンク先のデータを読めなくなるためです。省略すると「再インストールしても空のまま」という状態になり、修復できなかったように見えます。

復元後は次のように確認できます。

```bash
find ~/Library/Containers/<Bundle ID> -maxdepth 6 -type l -exec readlink {} \; 2>/dev/null
# 没有输出，或输出里没有 /Volumes/... 就对了
```

### 手順 2：アプリ本体をローカルに戻す

アプリ本体も外部ドライブへ移行している場合だけ必要です。その場合、`/Applications` にあるのは AppPorts の起動用シェルです。直接上書きインストールするとシェルが置き換わり、外部のコピーが使われないまま残ります。修復パネルの「ローカルに戻す」をクリックするか、「外部ドライブ」で対象を選択して「ローカルに戻す」を実行してください。再インストール後も外部に置きたければ、アプリ本体をもう一度移行できます。

### 手順 3：アプリを再インストールする（開けない場合のみ）

macOS 27 でも正常に開ける場合は、この手順を省略し、手順 4 でデータをマウント移行へ切り替えられます。再インストールが必要な場合は、アプリを完全に終了し、公式の配布元から上書きインストールします。App Store アプリは App Store を使用します。パネルの「App Store を開く」から開けます。公式サイトのアプリは公式サイトからダウンロードしてください。**コンテナディレクトリは削除しないでください。** 再インストールでは変更されないため、チャット履歴もログイン状態も残ります。

インストール後、パネルの「再チェック」をクリックするか、最初の確認コマンドで署名が `Authority=Developer ID Application: ...` または `Apple Mac OS Application Signing` に戻ったことを確認してください。署名が戻ると「署名置換済み」バッジが消えます。通常のスキャンではバックアップを保持し、AppPorts で復元を完了したときだけ対応するバックアップを削除します。

::: tip 完全なバックアップは直接復元できます。旧形式には元のアプリが必要です
新しい「Restore Original Signature」は、元のアプリ全体のバックアップを使用するため、開発元の秘密鍵は不要です。旧形式の署名 ID の名前しかない記録では直接復元できません。同じバージョンの公式の `.app` を選択するか、上記の手順で再インストールしてください。どの方法でも、先にクラシックモードのコンテナデータを復元する必要があります。[署名のバックアップと復元](/ja/datamigrae/resign#署名のバックアップと復元)を参照してください。
:::

### 手順 4（任意）：マウント移行でデータを外部ドライブへ戻す

再インストール後に AppPorts を開くと、コンテナディレクトリには「Migrate」の代わりに「マウント移行」が表示されます。クリックして案内に従ってください。アプリの初回起動時にはリムーバブルボリュームへのアクセス許可を求めるダイアログが出るので、**許可してください**。外部ドライブは暗号化されていない APFS である必要があります。AppPorts が先に確認して次の操作を案内します。APFS でなければ、データをローカルに残しても問題ありません。[外部ドライブに APFS が必要な理由](/ja/why-apfs#what-to-do)を参照してください。

## 避けるべき対処

| 対処 | 解決しない理由 |
|------|-----------|
| データをローカルに戻すだけで修復完了とする | 復元は外部データを読めない問題だけを解決し、署名は直さない。再署名したアプリは復元後もすぐ終了する |
| 「Resign This App」をもう一度実行 | 再署名自体が原因であり、エンタイトルメントを再び消すだけ |
| アプリにフルディスクアクセスを付与 | コンテナの検証を回避できる場合もあるが、キーチェーンの権限は失われており、ログイン状態の問題は残る。一時的な手段にすぎない |
| ターミナルから開ければ修復済みと判断 | ターミナルの権限を借りて起動しているため、修復できたように見えるだけ。Finder / Dock から開けるかで判断する |

## AppPorts 1.8.2 の変更点

- コンテナディレクトリはシンボリックリンク移行をやめ、メインプログラムがサンドボックスかどうかに関係なく、[マウント移行](/ja/datamigrae/mount-migration)を使います。
- 右クリックメニュー、「Re-sign after migration」、ログイン時の自動再署名スクリプトのすべてで、サンドボックスアプリの再署名を拒否します。
- 「Restore Original Signature」は、元のアプリ全体とその署名、エンタイトルメントの復元に変わりました。開発元の秘密鍵は不要です。旧形式の記録では、同じバージョンの公式アプリを選択できます。
- 署名が置き換えられたアプリを自動検出します。赤い「署名置換済み」バッジ、起動時の通知、右クリックの「修復手順を表示」から開く修復パネルを提供します。
- 旧版で作成したコンテナのシンボリックリンクも「Linked」として認識し、「Restore」は引き続き使えます。シンボリックリンクを作り直さないよう、コンテナでの「整理」「再リンク」は無効になります。
- 旧方式に依存するユーザー向けに、**クラシックデータ移行モード**を残しています。デフォルトはオフで、有効化にはリスクの確認が必要です。[設定](/ja/settings#classic-data-migration-mode)を参照してください。APFS でない場合は、コンテナデータをローカルに残すことをお勧めします。そのためにクラシックモードを有効にする必要はありません。

すでに再署名されたアプリは、AppPorts のアップグレードだけでは自動で元に戻りません。上記の手順で対処してください。

## よくある質問

### チャット履歴は失われますか？

失われません。再インストールでコンテナデータは変更されず、アプリは元のデータを引き続き読みます。この処理全体で AppPorts がデータを削除することもありません。

### データを復元しても開けません

署名がまだ修復されていないためです。データの復元とアプリの再インストールは独立した手順で、両方必要です。[修復](#修復)を参照してください。

### WeChat だけで起きる問題ですか？

そうとは限りません。同じ macOS 27 でも、再署名した QQ Music は正常に開けました。現在の証拠は「システムにそのアプリの古い署名の許可記録があるか」を示していますが、事前の判定はできません。そのため、署名を置き換えたアプリをすべて一覧にして確認できるようにします。[アップグレード前の確認](#アップグレード前の確認)のスクリプトで一覧を取得できます。

### AppPorts がデータを壊したのですか？

データは正常です。ただし、問題の直接の原因は確かに、旧版 AppPorts で再署名に同意する選択肢があったことです。1.8.2 ではこの手順を廃止しています。
